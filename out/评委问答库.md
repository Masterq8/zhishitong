# 智审通 — 评委可能提问与答辩参考

## 技术深度类

**Q1：为什么不让 AI 自动审批？**
> 高校审批涉及责任归属和制度合规。AI 可以做材料理解、政策检索和风险提示，但不能替代行政人员做最终决定。本系统采用 Human-in-the-Loop 设计，AI 的输出是证据和建议而非行政结论，最终审批权始终保留在审批人手中。这既是对行政责任的尊重，也避免了黑箱 AI 自动审批的合规风险。

**Q2：和普通 ChatGPT 套壳有什么区别？**
> 普通 ChatGPT 是对话工具，而智审通把 AI 嵌入真实审批流程。系统包含 OCR 材料识别、表单 Schema 映射、字段归一化、RAG 政策依据检索、逐项合规检查、多阶段审批流转、通知推送和审计日志，AI 输出不是孤立回答，而是驱动业务流程中的可解释辅助信息。项目代码约 17,000 行，含 99 个 API 端点和 16 张数据表，不是简单的 API 封装。

**Q3：为什么还要本地模型？云端模型不是更强吗？**
> 本地模型提供三个云端无法替代的能力：(1) 隐私可控——合规分析涉及的政策条文和申请数据不出服务器；(2) 离线可用——校园网环境复杂，云端 API 不稳定时本地模型继续服务；(3) 成本可控——高频调用场景下本地推理没有 API 费用。系统采用分层策略：云端负责复杂语义抽取，本地负责可控的合规分析，规则兜底保证基本可用。

**Q4：云端模型不稳定怎么办？**
> 系统做了三层降级：自然语言填表优先云端 LLM，失败时走规则兜底（正则匹配「明天/后天」「长途汽车」「公假」等高频表达）；OCR 有多模态 LLM → EasyOCR 降级链；RAG 合规分析有本地 Qwen3-14B 兜底；API Key 池记录失败计数并自动禁用异常 Key。这意味着单点故障不会阻断核心审批流程。

**Q5：RAG 为什么用 TF-IDF 而不是向量数据库？**
> 选择是务实的：(1) 政策知识库的规模在百条级别，TF-IDF 的字符级 n-gram 匹配已经足够精准；(2) TF-IDF 不需要 GPU/Embedding API，降低部署门槛；(3) 匹配结果可解释——可以直接展示匹配到的政策原文，不需要解释向量相似度的含义。生产环境中可以升级为向量检索，但当前方案在准确性、可解释性和部署复杂度之间取得了良好平衡。

**Q6：如何处理 OCR 对不同类型文档的识别？**
> OCR 采用多级路由策略：多模态 LLM (qwen-vl-max) 一步到位处理复杂图片 → 图片自动 EXIF 修正和压缩（最大边 1800px, JPEG 85）→ 字段名映射归一化 + 正则兜底提取 → EasyOCR 降级。PDF 文件先尝试 pypdf 文本直提，扫描件自动转图片后再走 OCR 管线。后端通过 `_normalize_json_keys` 将 LLM 输出的中英文混合字段映射到模板标准 key。

**Q7：19 类审批模板的流程是如何设计的？**
> 模板引擎采用 JSON 驱动设计（templates.json），每类模板定义字段 Schema、审批阶段（部门→财务→学校）、金额阈值自动跳过规则。workflow.py 中定义了事务流程的编排逻辑，支持动态跳过无需审批的阶段。新增事务类型只需在 JSON 中添加模板定义，无需改动代码。

## 创新性类

**Q8：这个系统的创新点在哪里？不是已有 OA 系统吗？**
> 传统 OA 系统是把纸质表单搬到网页上，并没有降低信息理解成本和审核成本。本项目的创新在于：(1) 将 AI 从问答工具转变为审批流程中的协同代理——AI 理解自然语言、检索政策、分析风险、生成建议，但最终决策权保留给人工；(2) 云端+本地+规则三层 AI 分层架构；(3) 玻璃拟态设计系统将 AI 能力可视化，让非技术用户能感知和理解 AI 的辅助作用。

**Q9：这个系统能扩展到其他学校吗？**
> 可以。系统从设计之初就考虑了多学校支持：用户带 school 字段、学校管理员边界限制、学校级服务等级（Pro/Free）。政策知识库和审批模板是 JSON/规则配置，替换学校政策和审批模板即可迁移。系统还支持 MLX LoRA 微调管线，可利用目标学校的历史审批数据微调本地模型。

## 工程完成度类

**Q10：如何保证系统安全性？**
> 系统实现了多层安全防护：JWT 双令牌机制（access + refresh）、bcrypt 密码哈希、Fernet 密钥加密存储 API Key、文件上传 MIME 魔数校验防止伪造、软删除机制保护数据可恢复、全链路审计日志记录所有敏感操作。生产部署时 JWT_SECRET 和 ENCRYPTION_KEY 必须通过环境变量配置。

**Q11：系统如何做性能优化？**
> 图片 OCR 前自动 EXIF 修正和压缩（最大边 1800px, JPEG 85），PDF 文本直提避免不必要的 OCR，Redis 缓存 OCR 结果和限流计数，服务端分页避免大数据量传输，TF-IDF 矩阵磁盘缓存避免每次重启重建，LoRA 微调模型通过 GGUF 量化加速本地推理。

**Q12：项目的测试情况如何？**
> 后端目前有 16 个测试用例，覆盖手动合规接口、账号意图预填、正则兜底、OCR 图片预处理等核心场景。前端暂无自动化测试。项目还包含预发布验证脚本和敏感信息扫描，作为 CI/CD 的一部分。测试覆盖是后续改进的重点方向。

**Q13：为什么选择 SQLite 而不是 PostgreSQL？**
> 比赛演示场景下 SQLite 的零配置部署优势明显——不需要单独安装数据库服务，评委可以在任何环境一键启动。生产环境中可以无缝切换到 PostgreSQL，因为 SQLAlchemy ORM 屏蔽了数据库差异，只需修改连接字符串。

## AI 能力边界类

**Q14：AI 的合规分析准确率如何？如何评估？**
> 合规分析当前是辅助性而非判决性的——AI 提供风险等级、逐项检查、政策引用和建议动作，但不做最终合规判断。准确率的衡量维度包括：政策检索的召回率（相关条文是否被找到）、风险判定的合理性（是否与人工判断一致）。系统通过审批人的采纳/覆盖行为隐式收集反馈。LoRA 微调管线为未来基于真实审批数据的模型优化提供了基础。

**Q15：如何避免 AI 产生幻觉？**
> 三层约束：(1) RAG 检索要求 AI 只能基于检索到的政策条文生成分析，prompt 中明确要求引用具体条款；(2) 合规检查项（必填字段/范围校验/重复检测）由规则引擎硬性执行，不依赖 AI；(3) 审批人始终可以看到 AI 的输出依据（政策引用原文），可以核实和覆盖。这种「AI 建议 + 规则约束 + 人工决策」的机制有效降低了幻觉风险。

## 实用性与局限性类

**Q16：这个系统离实际部署还有多远？**
> 系统已具备基本可部署性：完整的用户-角色-权限体系、16 张数据表、系统监控、安全机制、一键启停脚本。主要差距在：(1) 需要配置生产级数据库（PostgreSQL）；(2) 需要部署 Redis 服务；(3) 需要配置云端 LLM API Key；(4) 本地推理服务需要 GPU 服务器部署 Qwen3-14B GGUF 模型；(5) 前端和 API 需要增加自动化测试覆盖。

**Q17：为什么不直接做成纯 SaaS？**
> 高校场景有两个特殊性：一是数据隐私——学生和审批数据涉及个人信息保护，许多学校要求数据不出校；二是网络环境——校园内网复杂，纯 SaaS 依赖外部 API 可用性。本系统采用「云端增强 + 本地核心」的混合架构，既利用云端大模型的能力，又保证核心审批流程和数据在本地可控。

**Q18：19 类审批模板的字段和流程如何维护？**
> 模板采用 JSON 配置文件驱动（templates.json），字段 Schema 和审批阶段均可通过修改 JSON 配置来维护。管理员界面（数据管理页）提供了可视化入口。未来可以增加模板编辑器，让学校管理员不写代码就能定制审批模板。

**Q19：前端为什么要花精力做玻璃拟态设计？**
> 因为系统的用户是学生、审批老师和管理员——他们不是技术人员。前端的视觉语言决定了他们能不能快速理解和信任系统。玻璃拟态设计系统不是装饰，而是功能性的：(1) AI 面板的渐变边框让用户感知到「这是 AI 生成的建议」；(2) 背景流体场在 AI 调用时动态变化，提供调用状态的可视反馈；(3) 角色化导航降低不同角色用户的学习成本。

**Q20：项目最大的局限性是什么？**
> 三个主要局限：(1) 本地推理服务依赖 28GB 的 GGUF 模型文件，对部署硬件要求较高，后续可探索更小的量化模型；(2) 政策知识库目前是静态 JSON，需要手动维护，未来可加入自动爬取和更新机制；(3) 缺少真实用户测试数据，AI 效果评估主要基于开发者的主观判断，需要在实际校园环境中收集反馈迭代。

## 扩展性问题

**Q21：如何支持更复杂的审批流程（如会签、转办、条件分支）？**
> 当前 workflow.py 的流程编排支持顺序审批和金额阈值跳过。会签（多部门并行审批）和条件分支（根据事务属性动态选择审批路径）可以在现有架构上扩展：workflow.py 中增加并行节点和条件节点类型，审批记录模型中增加并行审批状态追踪。核心挑战不在技术实现，而在高校实际审批规则的梳理和建模。

**Q22：项目的 LoRA 微调管线有什么实际价值？**
> LoRA 微调管线（MLX 训练 → 融合 → GGUF 转换）的实际价值在于：(1) 可以利用目标学校的历史审批数据微调模型，提升领域适配性；(2) MLX 框架在 Apple Silicon 上高效运行，降低训练门槛；(3) 自动融合和 GGUF 转换实现了训练到部署的一键流程。PEFT 管线保留为跨平台备选，覆盖 Windows/CUDA/CPU 场景。
